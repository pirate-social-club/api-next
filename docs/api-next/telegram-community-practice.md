# Community Telegram practice

This source adds per-community practice without changing the staging pilot or enabling an environment. Existing compact configuration remains valid. The existing community management Telegram page owns bot connection and the Study setting. Bot tokens continue through the masked owner input and encrypted integration record.

An owner saves Study intent through POST /communities/:communityId/telegram/study, using the existing integration revision and idempotency ledger. Browser session, Origin and CSRF rules apply. Ownership is checked before replay and again in the save transaction. Enabling requires a ready bot, but no publishing channel or assistant credential. The saved intent names the current numeric bot ID. Same-bot token rotation preserves intent; replacement and disconnect clear it. Saving intent does not imply environment availability or song eligibility.

The separate compact fields community_practice_enabled and community_practice_policy_revision delegate community practice. They default off/absent and cannot be combined with the staging pilot's practice_enabled. Community practice requires staging or production, learner audio storage, usable transcription configuration and the normal Telegram queue/vault/runtime admission. The original pilot still requires staging, its one explicit community and at most eight explicit songs. No checked-in environment enables the new mode.

The learner catalogue is distinct from corpus readiness. Migration 0334 introduces an unseeded append-only decision ledger. Each decision binds community and post, audio, lyrics and language-profile revisions, content rating, learner band, learning language, exercise type, policy revision, disposition and reviewer-role/evidence provenance. New decisions must advance the per-song revision by one. Updates, deletes and truncation refuse. Scheduling is deliberately unsupported: future effective_at values refuse, and recorded_at comes from the database clock. No accepted policy, real song decision or reviewer authority is supplied by this migration. The existing policy-maintainer record still governs that acceptance.

Only the latest decision can authorize selection. Missing, ineligible, fixture-only, stale or differently delegated decisions produce no learner catalogue entry. An old eligible decision never becomes a fallback. This first Telegram presentation remains English say_it_back with no learner band or helper-language selection. General publication, active community, ready lyrics, both stems, current revisions, accepted language profile and at least four distinct eligible exercises remain additional requirements. Neither an owner toggle nor a successful corpus query grants lesson approval.

Native installation strips ambient default grants from the new table and trigger function and pins the function search path. The serving role then needs an explicit SELECT grant on study_learner_catalogue_decisions and must have no INSERT, UPDATE, DELETE, TRUNCATE or owner-equivalent authority there. The normal runtime checks this before composing community practice. The roles example documents these privileges; actual grant changes remain part of reviewed environment preparation. There is no learner or community-owner endpoint for recording decisions.

GET /communities/:communityId/telegram/study/catalogue is owner-only and private/no-store. It distinguishes unavailable community practice from an available but empty catalogue. Selection uses eight-song keyset pages in post-ID C collation. Chat cursors stay in leased server state, and each page rotates the expiring selection token. A direct post query rechecks selection, including a song beyond page one. At session acceptance, the integration and community locks protect owner intent and bot authority; decision appends take the matching community lock. Current eligibility is checked again in the same Study transaction.

Every new session in this increment remains practice-only, including linked accounts. Migrations 0239 and 0246 are unchanged. Existing Study sessions, completed history and reward rules are not rewritten. Recovery and prospective rewards remain a later increment.

Qualification includes actual PostgreSQL serving-role reads and session creation, missing intent, bot mismatch, disable, latest denial and reconnect refusal, immutable decision history and a real ninth-song start. The unchanged pilot webhook and restricted-learner suites remain acceptance checks. Source qualification does not establish production bot integration, secrets binding, policy acceptance, activation, phone acceptance of this new mode or financial acceptance.

The existing Telegram integration response is unchanged. The new Study command and catalogue read return `integration` plus `enabled`, binding current-bot intent to the integration revision. Candidate client 0.141.0 is retained as rejected compatibility evidence; 0.141.1 supersedes it without changing its bytes.
