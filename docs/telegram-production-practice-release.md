# Production Telegram practice release

This fixed operator entry prepares the accepted Telegram application for the
production community. It is separate from the application reader, the website
preparer, and the spent public-post and Rewards release operations. It does not
select arbitrary sources, accounts, databases, Workers, songs, or secrets.

`TELEGRAM_RELEASE` pins application5a121865, both distinct serving baselines,
both compiled modules, the full qualified input closures, migration334, the nine
missing grant sets, and the canary community and post. Application source and
configuration remain immutable. Phase configurations belong in the new operation
packet. The website companion must inherit the accepted membership diagnostic
fix and contribute its exact guarded prepared receipt and actual serving baseline.

## Local source qualification

Run `bun scripts/telegram-production-release.ts preview` for a filesystem-only
source and configuration preview. It reads local Git objects and qualified files.
It does not fetch, authenticate, connect to a database, initialize a journal, or
call a provider. `operational_ready:false` means the preview is not an operational
approval. No source acceptance or historical date grants production authority.

The process probe invokes only the maintained timeout handshake and local tool
identity checks. Invoke its executable and script with absolute paths, as required
by the shared process identity check. `probe` and `probe-child` have no provider or
database adapter path. Preserve every failed and successful probe receipt.

The PostgreSQL test uses a strict loopback URL, a UUID-named disposable database
and role, and the exact migration334 SQL over minimal dependency tables. It tests
ledger checksum refusal, ambient grant removal, the exact pre/post privilege
matrix, forbidden column authority, runtime denials and immutable decisions. Its
synthetic preceding ledger is not proof of historical schema installation. The
application's existing full-schema Telegram PostgreSQL tests provide that separate
coverage. Both fixtures must pass; neither substitutes for an actual runtime-role
production observation.

## Independent review and scope authority

Every live mode requires a hashed independent `TelegramReview`, a separately
hashed `TelegramAdmission`, and the exact fixed phase. The review binds the
existing task-specific owner instruction and its digest, the community and song,
permitted actions, source and tool identities, qualified files, backup, website
receipt, credential contract, catalogue acceptance, phase configurations and
recovery targets. Derive the authority record from the actual owner instruction;
do not manufacture a new approval or require renewal merely because it is dated.

Technical admission is separate. It names the exact fixed resources, grants
exclusive observation or effect access, and has a current finite start, execution
and recovery window. All live commands execute beneath the shared Linux process
identity and timeout supervision. A local source task never supplies live access.

`initialize` accepts only an independently reviewed new-operation evidence request.
It creates the new fixed directory, journal and genesis once. Existing or partial
directories are preserved and refused. Review binds their real directory identities.
No old journal, attempt, resolution or history is cleared or retargeted.

`observe`, `execute`, and `resolve` require exactly these options:

```
--phase PHASE --review ABSOLUTE_FILE --review-sha SHA256 \
--admission ABSOLUTE_FILE --admission-sha SHA256
```

Use the absolute Bun executable and absolute script path for a supervised live
invocation. No token or database URL belongs in argv, a review, or a receipt.
The maintained operator environment supplies only the two fixed database selectors.
Child environments retain their existing narrow allowlists. The wrapping secret
stays in the service folder, never the operator folder. Adding it does not require
changing the existing website preparer's strict operator environment contract.

managed create-only contract. The installed CLI `secrets set` is an upsert and is

The create-only contract uses `telegram-managed-create-only-contract-v2` with

Install Jobs and HTTP disabled, verify both, then enable connect-only in the same

The final native acceptance requires current-bot owner intent; global activation
does not require that intent in advance. Linking, the staging pilot and Rewards
stay disabled throughout.

Every phase durably creates an exclusive attempt before its effect and rechecks
admission and state immediately beforehand. A lost upload or COMMIT reply leaves
that attempt unresolved. `observe` records no effect. `resolve` binds an independent
review of the exact attempt and current read-only observation, and can append
verification without repeating the effect. A confirmed non-application never
silently permits replay in this spent namespace.

The narrow pause-intent phase requires its exact owner database identity, canary, revision and history checks, and skips provider-origin and global-inventory readiness. This permits disabling that intent when forward readiness fails. Later Worker phases still require their applicable fresh provider and inventory checks.

Recovery has a separate pause-intent transaction before either Worker pause
upload. It updates both integration revisions consistently, so a committed intent
pause remains independently resolvable if a later upload fails. It then disables
both Workers' practice and runtime flags. Only after both pause phases are verified can it restore a reviewed
compatible disabled version. It does not require successful candidate acceptance. Retained module/config bytes
and current control/process/admission are checked immediately before pause upload.
Recovery observations use metadata only and never fabricate a live module hash or claim full readiness. Retained recovery targets keep their independently reviewed compiled-byte proof. Forward acceptance still fetches actual compiled bytes through the maintained managed API transport, without a PATH-selected credential recipient. Recovery resolution binds the exact serving version, and unseen newer uploads
remain visible even when their semantic configuration equals the current one.
Queued, in-flight or uncertain work blocks traffic restoration until it has been
reconciled read-only. Keys, migrations, catalogue decisions and Study history are
retained. Recovery never deletes queued or immutable history to make a check pass.

The separate `recover-baseline-http` and `recover-baseline-jobs` route restores only
